## Part A: sabha-ai server change: live drafts for apps

### Why

`AgentDraftChannel` is broadcast only by `Agent::Turn` (`app/models/agent/turn.rb:916-936`),
and the client (`app/javascript/controllers/agent_draft_controller.js`) and its shell template
(`app/views/agent/turns/_draft*.html.erb`) have the single built-in agent baked in. They're
mounted only when `Agent.configured? && room.agent_drafts_in_place?`
(`app/views/rooms/show.html.erb:33`). An app has no way to publish a draft today.

The payoff: a transient, non-durable draft that the finished message replaces in place
(shared DOM id `message_<client_message_id>`). No edit churn in message history, no
`message_updated` events to other bots, no preview delete/repair logic in the plugin.

### Design

1. **Cable action `draft` on `AppEventsChannel`** (the app is already connected; no new REST).
   ```json
   {"action":"draft","draft_id":"<uuid>","room_id":123,"parent_message_id":456,
    "kind":"start|text|activity|end","text":"…","title":"…","seq":7}
   ```
   - `draft_id` is generated by the app (UUID v4) and later becomes the final message's
     `client_message_id`.
   - Authorization uses the same reach as posting: the app must be able to post to
     `room_id`, and `parent_message_id` must be a top-level message in that room. Refusal
     is sent back on the channel as `{"event":"draft_refused","draft_id","error"}`,
     mirroring `answer_refused`.
   - Target: `parent_message_id` present → `AgentDraftChannel.broadcast_to(parent_message, …)`
     (the provisional thread panel); otherwise `broadcast_to(room, …)`. This is the same
     fork as `Agent::Turn#draft_target`.
   - Limits: text capped (e.g. 16 KB), at most ~10 broadcasts/s per draft. Excess is
     dropped silently, because a newer snapshot supersedes it.
2. **Snapshot text, not deltas.** OpenClaw previews may rewrite earlier text. Add a
   `text` kind that *replaces* `.message__draft-text` (the existing `chunk` appends).
   Built-in agent behaviour is unchanged.
3. **Per-app shell.** On `start`, the server renders `agent/turns/_draft` with `bot: app`
   and broadcasts `{kind:"start", turn_id, html}`. The client inserts `html` when present
   and otherwise falls back to its template. Name, avatar and role badge are then correct
   for any app.
4. **Mount the draft controller wherever an app can draft**: rooms, threads and DMs where an
   app is a member, plus the provisional thread panel (`rooms/threads/new.html.erb`). It is
   no longer gated on the built-in agent being configured.
5. **`client_message_id` on `POST /api/v1/rooms/:id/messages`** (JSON envelope key, UUID only,
   unique per room). The created message carries the draft's DOM id and replaces the shell
   in place. `kind:"end"` tears down a draft that produced no message.
6. Tests: channel tests (authorize/refuse/target fork/limits), API create with
   `client_message_id`, system test of an app draft streaming then replaced.
   Document it in `docs/features` and the APPS/skill docs.

Open server questions (answered while building Part A):
- Top-level mention with `replyToMode` threading: the built-in agent shows a "replying…"
  pill on the mention (`refresh_replying_pill`). Do apps get the pill in v1? Proposal:
  not in the first cut; the thread panel streams and the room shows the reply when it lands.
- Typing: the app typing whisper (`TypingNotificationsChannel`) is undocumented and may
  not relay in production (`ANYCABLE_STREAMS_WHISPER` unset). Proposal: the draft `start`
  shell *is* the working indicator, and the plugin drops whisper typing entirely.

## Part B: plugin rebuild

### Sabha wire contract the plugin targets (summary)

- **Auth.** REST `{origin}{/workspaceId?}/api/v1`, `Authorization: Bearer sabha_app_…`.
  Cable `wss://{origin}/cable` with the same header; SaaS adds `?wid=<workspaceId>`.
  `GET /me` probes the key and returns the bot id.
- **Events.** `message_created|updated|deleted`, `reaction_created|deleted`,
  `user_created|deleted` (others ignored for now). Use `mentions_app`,
  `mentionees[{id,name}]` and `body.markdown` for the agent, and never parse HTML for mentions.
- **Send.** JSON `{body: html, client_message_id?}` with `@{id}` mentions;
  `?parent_message_id=` threads; multipart `attachment` for files (no caption: a file posts
  alone). 60 creates/min → honor 429 `Retry-After`.
- **Edit/delete.** `PATCH`/`DELETE /messages/:id` (creator only).
- **Reactions.** `/messages/:id/reactions` (was `/boosts`).
- **Read/search.** Cursor paging (`before`/`after`/`limit≤200`); search uses `room_ids[]=`
  (fixes the old bug).
- **Setup.** No `/join/:code` self-registration. An admin creates the app in Sabha and
  pastes URL and key.

### Architecture (2026.11.1 SDK)

Patterned on `extensions/mattermost` (structure) and `extensions/slack` (gateway v2, preview
custody), using **public `openclaw/plugin-sdk/*` subpaths only**. Both references use
bundled-only APIs we must not copy.

- **Entries.** `index.ts` uses `defineChannelPluginEntry`; `setup-entry.ts` uses
  `defineSetupPluginEntry`. The setup-only plugin (`channel.setup.ts`) is spread as `base`
  of the full plugin, and transport/runtime modules load lazily.
- **Gateway v2.** `createChatChannelPlugin<…, 2>`: the host-owned scheduler owns heartbeat
  and backoff timers. `ready` is reported only after the `AppEventsChannel` subscription is
  confirmed; a close before confirmation counts as a failure so backoff applies. Handshake
  timeout and payload size limit are bounded (Mattermost pattern).
- **Durable ingress.** `createStandardRawEventIngressMonitor` with tombstone dedupe on the
  message id replaces the hand-rolled FIFO dedup. Self echoes are filtered before enqueue.
- **Access.** `runtime.channel.inbound.ingress.resolveStable` feeds its exact result once
  into `runtime.channel.inbound.buildContext` from the same runtime.
  `contextBinding.nativeChannelId` must match. Top-level groups require `mentions_app`;
  DMs and existing threads don't. DM allowlist is enforced before drafts/media.
- **Media.** Download signed attachment URLs right after admission with
  `saveRemoteMedia` (replacing the deprecated `fetchRemoteMedia`). SSRF guard stays on by
  default; private hosts are an explicit per-account opt-in.
- **Sessions.** Unchanged model: group peers include account id; DMs use
  `per-account-channel-peer`. Thread events name their thread room.
- **Live preview.** `createLivePreviewLifecycle` from `channel-outbound` with a Sabha
  draft transport:
  - Preview start/update → cable `draft` start/text (coalesced, unchanged-text skipped).
  - Final → `POST` with `client_message_id = draft_id` (first chunk; later chunks are plain
    posts).
  - Cancel / silent / failure / no-text → `draft end`.
  - Media finals end the draft, then post files.
  - Modifying reply/message hooks disable text previews but keep the `start`/`end` working
    shell.

  No preview message ever exists, so there is no edit/delete/repair path. (Phase 0 checks
  that the lifecycle accepts a non-message preview transport.)
- **Outbound formatting.** Markdown → Sabha HTML (Lexxy-safe tags) with code-fence/list-aware
  chunking. `replyToMode: off` and DMs reply inline; threaded replies post to the parent
  room with `parent_message_id`.
- **Message actions** (TypeBox schema, authority taken from host context only): send, edit,
  unsend, react, thread-reply, search, member-info, read, reactions. The `read` result shape
  stays `{messages, hasMore, nextCursor}` for the host formatter.
- **Directory/resolver.** Room/user listing, one account at a time; lookup failure is kept
  distinct from an empty result.
- **Tools.** `sabha_search_members`, `sabha_create_dm`, using tool context v2 with
  `assertInvocationCurrent()`.
- **Config.** `channels.sabha.accounts.<id>`: `url`, `appKey` (secret), `workspaceId?`,
  `allowPrivateNetwork?`, DM policy/allowFrom, rooms map, `replyToMode`, `streaming`.
  Shared non-credential settings may sit at channel root. Bot identity comes from `/me` at
  startup and is never written back to config.
- **Setup.** The wizard and `openclaw sabha setup` take URL + key, verify with `/me`, and
  write the named-account shape. The manifest generator emits
  `channelConfigs.sabha` + `cliCommands`.

## Phase 0 results (2026-11-07)

Against the local sabha-ai dev server with a throwaway app (`OpenClaw Spike`, bot 508, room 3):

- `GET /api/v1/me` → `{id, name, workspace:{name,url}}`. Cable `ws://localhost:8080/cable`
  accepts `Authorization: Bearer` alone; `AppEventsChannel` subscription confirmed.
- An unknown cable action (`draft`) is silently ignored: no error frame.
- A top-level mention arrives as `message_created` with `mentions_app:true`,
  `mentionees:[{id,name}]`, `body.{html,plain,markdown}`, `room.{id,type:"Open",has_app}`,
  and `user.{id,name,role}`. A top-level message without a mention is **not** delivered.
- `POST /rooms/3/messages?parent_message_id=4214` → `201 {id:4216, room_id:221}`.
  A human follow-up in thread 221 arrives with `thread:{id,parent_message_id,parent_room_id}`
  and `room.type:"Thread"`.
- Frames carry AnyCable reliable-stream metadata `stream_id/epoch/offset`. The plugin should
  resume from the last offset on reconnect (AnyCable `history` command) instead of losing
  events; durable ingress dedupe covers any replay overlap.
- `createLivePreviewLifecycle` (`src/channels/message/live.ts`) is transport-agnostic. The
  draft is `{id, flush, seal?, discardPending?, clear}`, and finalize-in-place is
  `editFinal(id, edit)`. Sabha maps `id()`→`draft_id`, `editFinal`→`POST` with
  `client_message_id`, `clear`→`draft end`. **Fits.**
- `runtime.state.openChannelIngressQueue` is scoped by plugin id with no origin gate
  (`src/plugins/registry-runtime.ts:195`). Usable from an npm plugin, and the plugin id must
  be `sabha`. Runtime confirmation happens in Phase 7's packed host test.
- Not yet captured: attachment, reaction, and edit/delete payloads. These are checked in the
  Phase 7 end-to-end run.

## Resolved questions (2026-11-07)

1. **Typing:** no whisper typing; the draft's "Thinking…" shell is the only working indicator.
2. **Top-level threaded replies:** no "replying…" pill on the mention for apps in v1.
3. **Thread mentions:** fix in Part A. A mention of the app inside a thread reaches the app
   when the app can reach the thread's parent room, even if it never posted in the thread
   (`notify_bots_test.rb:68-81` changes accordingly). The app must then be able to read and
   reply in that thread.

## Implementation decisions (Phases 3–5, 2026-11-07)

- **Ingress identity.** `message:<id>`, `edit:<id>:<updated_at>`, `react:<reaction id>` /
  `unreact:<reaction id>`, one lane per room (`room:<id>`). Self echoes, deletes, `user_*`
  and unaddressed top-level messages never enter the queue (`src/monitor/events.ts`).
- **Edits and reactions** become `enqueueSystemEvent` context on the conversation's session
  after the same access check. They do not start turns. Deletes are dropped: the author
  meant the body gone.
- **Draft cleanup.** The host lifecycle keeps undelivered previews on failure, which suits a
  posted preview but would leave a draft shell spinning. `reply.finish()` always sends
  `draft end` unless the final replaced the draft. A follow-up deferred to an active run
  (`deferredToActiveRun: "followup"`) skips cleanup because it replies later through the
  same delivery.
- **Partial finals.** If the first chunk (the one with `client_message_id`) lands and a later
  chunk fails, the lifecycle retains instead of falling back, so nothing is reposted.
- **Modifying hooks.** External plugins cannot see the hook runner (`plugin-runtime` is
  bundled-only), so text previews can't be disabled automatically when a
  `reply_payload_sending` / `message_sending` hook exists. The final always replaces the
  draft, so the hooked text wins. Operators whose hooks redact content should set
  `livePreview: false`. Document this in the README.
- **Outbound targets.** `threadId` (a thread is its own room) beats `to`; `replyToId` maps to
  `parent_message_id`; `user:<id>` / `@{id}` goes through `POST /direct_messages`.
- **`ws`.** Only `scripts/host-integration.mjs` still uses it. Move that script to
  `websocket-runtime` in Phase 7, then drop the dependency.

## Phase 7 results (2026-11-07)

- **Manifests** are generated from `src/config/schema.ts`, `src/config/setup-contract.ts`
  and `src/plugin/meta.ts`. `build` cleans `dist/` first, so stale output from the old
  layout cannot ship.
- **`ws` dropped.** `scripts/host-integration.mjs` uses `WebSocketServer` from
  `websocket-runtime`. In 2026.11.1, `inbound.run` takes its reply producer from the
  resolved turn, not from the loader's `runtimeOptions`, so the harness attaches the
  test producer in `resolveTurn` on its installed copy.
- **End to end against local sabha-ai** (app 508, AnyCable on :8080):
  - `sabha setup` and `sabha doctor` pass.
  - A mention gets exactly one reply in a new thread.
  - An unaddressed message is ignored.
  - A thread follow-up without a mention is its own session, and the reply stays in the thread.
- **Finding: the server has no live drafts.** sabha-ai rejects `client_message_id`
  (422) and drops `AppEventsChannel#draft`. The fallback posted correctly, but every
  reply paid a failed POST and partial text reached the server log. `livePreview` is
  now opt-in until Part A ships.
